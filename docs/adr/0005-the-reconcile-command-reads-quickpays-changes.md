# The reconcile command reads Quickpay's changes

The reconcile command is the backstop for callbacks that never arrive. It used to reconcile the oldest 100 pending payments created in the last 7 days, and that budget went to the wrong payments: with the default capture mode every order waiting for shipment holds an authorized payment for days, so the oldest 100 could all be authorized while the payments the command exists for (a processing one, or a new one whose authorize callback was missed) waited behind them. A payment created 10 days ago and captured in the Quickpay manager today was never reconciled at all. Now a run asks Quickpay which payments changed since the previous run (`GET /payments?timestamp=updated_at&min_time=…`, once per Quickpay account, that is per distinct api key) and reconciles the pending payments among them, stuck ones first, however old. A payment Quickpay hasn't changed can't be out of step with the store, so it costs no request. Each account is listed since its own watermark, which every run that lists the account moves on; a payment that fails goes on a retry list and is reconciled again by every run; an account without a watermark is listed over a fixed lookback; and one run reconciles at a time.

## Considered Options

The request counts are for a shop with 1,000 orders a day running the command every 30 minutes.

- **A fixed budget** (the old command): 100 payments a run, about 4,800 requests a day. Rejected: the budget is spent oldest first, mostly on authorized payments that haven't changed, so stuck payments wait behind them, and a payment older than the window is never reconciled whatever happens to it.
- **Every pending payment**, every run: about 3,000 a run (three days of orders waiting for shipment), so about 144,000 requests a day, nearly all about authorized payments that haven't changed, on the API live checkouts share. Quickpay documents no rate limits. Rejected for the cost.
- **Aging backoff**: every pending payment, reconciled less often the older it gets. Rejected: it needs a last-reconciled time stored per payment, it still spends requests on payments that haven't changed, and it sees late exactly the change it backs off from, a capture or cancel in the Quickpay manager days after checkout.
- **The change feed** (chosen): about 50 payments change at Quickpay in a run, and only the pending ones among them are read, about 1,400 requests a day. Quickpay can't sort the list by `updated_at` (it rejects `sort_by=updated_at`), so it is listed by id, which pages steadily while payments change.
- **Holding the watermark back for a payment that failed**, instead of a retry list, so the next run lists its change again. Rejected: one payment that keeps failing would hold its account's watermark back for good and widen every later run to the full lookback, which brings back the cost of reconciling every pending payment.

## Consequences

- **A watermark always moves on once its account was listed**, whatever became of the account's payments. Only an account that couldn't be listed keeps its previous watermark: its changes are listed again by the next run, the run fails, and the other accounts move on.
- **A payment that keeps failing is never dropped**, and there is no backoff: it is retried by its id on every run, one request a run, and reported with the time it first failed until it reconciles, someone fixes it, or it is no longer pending.
- **Without a watermark, a run looks back a fixed period.** The first run, a cleared cache, a new api key and `--full` list the changes of the last `--since` (default 7 days), and a watermark older than that is clamped to it. `--full` catches the store up after a database restore. `--limit` no longer applies to reconciling: the changed set is small, and a budget is what starved the stuck payments.
- **A cleared cache costs one fallback run.** The watermarks and the retry list are kept together in a cache pool the application can point at a persistent adapter, and are lost together. Losing them is safe: the next run lists the whole `--since` period, and a payment to retry whose change is older than that is listed again once it changes again. A run whose state the cache refuses to save fails; the previous state stays, and since its watermarks are older, the next run lists again what that run listed.
- **One run at a time.** Two runs at once would send the same requests, and the one finishing last would overwrite the other's retry list. A run that writes holds a run lock from the plugin's lock resource, so a shared store keeps runs on different servers apart; a run started while it is held skips and exits 0, so overlapping cron runs don't alert anyone. A dry run and the fraud report store nothing and take no lock.
- **The plugin relies on Quickpay's `timestamp=updated_at` filter.** Quickpay documents it only as a value in the enum of the list's `timestamp` parameter, so what it does was verified live (2026-11-16): a payment created before `min_time` and captured after it is listed, and an operation moves its `updated_at`. The plugin's tests script Quickpay's answers, so they can't notice should Quickpay change it.
- **The plugin relies on Quickpay answering deep `page` offsets.** A fallback run lists every payment changed in the last `--since`: about 7,000 for the 7-day default at 1,000 orders a day, some 70 pages of 100 or more. That Quickpay answers pages that deep, completely and in id order, is unverified. Should it refuse one, the account fails to list on every fallback run and keeps no watermark; should it cut the list short silently, the changes past the cut are missed until those payments change again.
- **Pending payments are matched by Quickpay payment id**, so a run needs no order prefix to find the Sylius payment of a listed one.
