# A Sylius payment is linked to its Quickpay payment only through its details

A Sylius payment is linked to its Quickpay payment by the Quickpay payment id stored as `quickpayPaymentId` in its details, which payum-quickpay writes when it creates the Quickpay payment. The plugin asked two questions of that link, "is this a Quickpay payment?" and "which Quickpay payment is it?", and answered them by different rules: the payment method's gateway in some places, the mere presence of an id in others, and five ways of reading the id (payum-quickpay's `Details`, `?? null`, `isset()` with `(int)`, `is_numeric()` with `(int)`, Twig's `is defined`). Sylius keeps a payment and its details when the customer switches it to another payment method, so a bank transfer chosen after the Quickpay window was opened still carried an id. The state machine processor took it for a Quickpay payment, ran the status check on the bank transfer's gateway, and refused to let the admin mark it paid. Now one module, `Quickpay\QuickpayPaymentIdProviderInterface`, answers both questions by one rule each: a payment is a Quickpay payment while its payment method has a Quickpay gateway configuration, whatever its details hold, and its id is read by payum-quickpay's `Details` (`hasPaymentId()`: present and not null; `paymentId()`: a positive int or a digit string). An id that can't be read is an error where an id is needed (reading the Quickpay payment, the reconcile lock, a capture) and never matches where payments are matched by id.

## Considered Options

- **A queryable link: a plugin table** of Sylius payment ↔ Quickpay payment id, kept in step with the details and backfilled by a command. It would let the shared callback endpoint find any payment by its Quickpay payment id, without the order number. Rejected: every store needs a migration and a backfill, a one-way door, for a gap that only opens when an order prefix changes.
- **A queryable link: a platform-specific JSON query** on the details column (MySQL's `JSON_EXTRACT`, PostgreSQL's `->>`). Rejected: Sylius' `details` is a Doctrine `json` column, so no portable DQL reads into it; it would be per-platform SQL without an index.
- **Fixing each reader in place**, each switching to `Details` and a factory check of its own, with the shallow `PaymentProvider` kept. Rejected: the rule stays spread over eight readers, which is how they drifted apart.
- **Changing payum-quickpay's convert** to use `Details::hasPaymentId()` instead of `isset()`. Not needed: on Payum's `ArrayObject`, which the convert uses, `isset()` is false for a null id, exactly `hasPaymentId()`, so it would cost a release for no change in behaviour.
- **The details only, read through one module** (chosen).

## Consequences

- **A payment switched to another payment method is no longer the plugin's.** The state machine processor leaves its `complete`, `refund` and `cancel` alone, the reconciler refuses it (`InvalidArgumentException`, before anything is locked or read), the admin order page shows no Quickpay panel for it, and a callback on its own callback url is answered 204 with a warning. Money Quickpay holds for it, say an authorization the customer made in a still-open payment window, is the merchant's to handle in the Quickpay manager; an unused authorization expires by itself.
- **Matching by Quickpay payment id is done in PHP over a known set of payments**: an order's payments (the shared callback endpoint, after the order number candidates) and the pending payments (the reconcile run's change feed). There is no lookup by Quickpay payment id alone.
- **A callback on the shared endpoint for a payment made under a since-changed order prefix stays a logged warning.** For a pending payment the next reconcile run catches the change, since it matches by Quickpay payment id; for one that isn't pending, a completed payment refunded in the Quickpay manager, say, nothing does.
- **Tampered ids can't attach a callback to the wrong payment.** Only payum-quickpay writes the id, always as an int, so an unreadable one only comes from another writer; it fails where it is needed and is never matched, so it can't end a reconcile run either.
